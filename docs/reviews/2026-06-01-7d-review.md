# Watchman 7-Dimension Code Review

> [!info] How this review was produced
> 19 dimension-scoped agents read the actual source across backend + frontend; every finding was re-checked by an independent skeptic that re-read the cited code (default-refute if unconfirmable). **124 findings raised, 113 verified** (11 dropped). The highest-severity findings were then re-verified by hand against the code before saving.

> [!warning] Reviewer corrections to the auto-generated draft
> Two inaccuracies in the agents draft were corrected in this saved version:
>
> 1. **`/config/export` does NOT leak plaintext secrets.** `ConfigStore.exportAll` (`apps/backend/src/config/store/ConfigStore.ts:454-466`) re-encrypts the payload under the on-disk master key; over the network an attacker receives ciphertext, not plaintext. `/config/import` likewise requires a payload that decrypts under that key. The unauthenticated-API finding was therefore re-scoped from **[critical]** to **[high]** (config tampering + SSRF + RCE-delivery-vector, not secret exfiltration).
> 2. **The auth removal is intentional**, recorded in [[017-remove-authentication-frontend-v2-migration|ADR-017]] (the draft cited a non-existent filename `017-single-user-trusted-network-posture.md`). `AGENTS.md` was never reconciled with it and still claims JWT/CSRF/rate-limiting exist.

## Watchman Code Review — Final Report

This report synthesizes a 7-dimension review (Security, Correctness, Performance, Architecture, Code Design, Testing, UX) of the Watchman backend and frontend. 124 candidate findings were raised; 113 were verified against code and retained. All claims below are backed by file:line evidence from the source tree. `docs/` describes intent; the code is treated as truth.

---

## Executive summary

**Overall health: poor on security, middling elsewhere.** Watchman is architecturally coherent (a BaseService/ServiceRegistry backend, a renderer/registry-driven frontend), but the review surfaced a serious gap between documented behavior and shipped reality. The most consequential finding is that the backend's **entire control plane ships with no authentication, no CSRF protection, and no rate limiting** — directly contradicting AGENTS.md's claim of "JWT via HTTP-only cookies, CSRF double-submit-cookie, tiered per-category rate limiting." None of those mechanisms exist in code. Combined with a default bind to `0.0.0.0`, simply running the binary exposes config read/write and service control to anyone on the network. (Note: `/config/export`/`/config/import` operate on payloads encrypted under the on-disk master key, so they are **not** a plaintext-secret leak — see the corrections callout above.)

Note: ADR-017 (`docs/adr/017-remove-authentication-frontend-v2-migration.md`) documents an intentional removal of auth for a single-user trusted-network posture. That makes this a deliberate posture, **not an accidental regression** — but AGENTS.md was never reconciled with it, so the source-of-truth docs actively misrepresent the security model. Either way, several adjacent gaps (command injection, no SSH host-key verification, broken TLS pinning) are real and exploitable regardless of the auth posture.

### If you do nothing else, fix these

1. **[high]** Unauthenticated HTTP API lets anyone on the network tamper with service configs, trigger outbound requests (SSRF), and reach the Pi command-injection path (unauthenticated RCE-on-relay). Intentional single-user/trusted-network posture per ADR-017; `/config/export`/`/config/import` are master-key-encrypted (not a plaintext-secret leak). The genuinely risky parts are the `0.0.0.0` default bind plus the RCE/MITM primitives below. (`apps/backend/src/transport/http/server.ts:27-71`, `routes/config.ts:43-124`)
2. **[high]** Command injection / RCE on the SSH relay via a config-controlled host/path interpolated into a remote shell command. Exploitable through the open config API. (`apps/backend/src/domain/services/raspberryPi/PiStatsCollector.ts:226`)
3. **[high]** SSH connections perform no host-key verification — credential/passphrase theft via MITM on any monitored host. (`apps/backend/src/infra/ssh/sshExecutorImpl.ts:75-83`, `sshPool.ts:113-121`)
4. **[high]** TLS certificate "pinning" validates a throwaway probe socket, not the data connection — the pin provides essentially no MITM protection. (`apps/backend/src/infra/http/pinnedClient.ts:17-19,54-64`)
5. **[high]** Four of thirteen services (Philips Hue, Alby Hub, Mac Mini, Raspberry Pi) **can never render** on the dashboard due to a camelCase-vs-lowercase service-kind mismatch between backend and frontend. A user-visible "configured it, see nothing" bug. (`apps/frontend/src/services/renderers/types.ts:5`, `config/bentoLayout.ts:28`)
6. **[high]** WebSocket auth is effectively disabled — `defaultVerifyToken` accepts any bearer token as user `anonymous`, leaking all home-lab telemetry to any reachable host. (`apps/backend/src/transport/ws/wsPlugin.ts:25-34`)
7. **[medium]** Reconcile AGENTS.md with ADR-017 and reality. The docs claim security controls that do not exist; new contributors and operators will trust them.

A second-order theme worth flagging now: several documented load-bearing backend abstractions — the **circuit breaker, the SWR cache, and the keep-alive HTTP agent pool** — are fully built but **never wired into the composition root**, so every poll and HTTP read hits live downstream services with no de-duplication or backoff.

## Security

**Assessment:** The dominant pattern is fail-open-by-default: HTTP routes have no auth hook, WS auth accepts anything, origin enforcement is off when unconfigured, and the server binds all interfaces by default. A second theme is missing transport authentication of peers (no SSH host-key verification, broken TLS pinning, a config value shelled into an SSH command). A third is weak at-rest key hygiene and pervasive doc/code drift on advertised controls (auth, CSRF, rate limiting, PII redaction — all documented, none present). Several medium/low findings are currently "inert" only because no real auth/cookies exist yet; they become live the moment auth is wired in and must be fixed together with the auth gate. Note ADR-017 documents the auth removal as intentional for a single-user trusted-network posture — but AGENTS.md was never updated to match.

### [high] Entire HTTP API is unauthenticated (intentional per ADR-017; risk amplified by the `0.0.0.0` default)

`buildServer()` registers only logSampling, requestTimeout, compress, errorHandler, and route plugins — no auth `onRequest`/`preHandler`, and no `@fastify/jwt`/`@fastify/cookie` is installed. Every handler runs anonymously: create/modify/delete service configs, `POST /config/import`, `GET /config/export`, `GET /config/audit`, and `POST /services/:kind/control`. **Correction to the original draft:** `/config/export` and `/config/import` operate on payloads encrypted under the on-disk master key (`ConfigStore.exportAll`/`importBundle`), so they do **not** hand out or accept plaintext secrets over the network — the at-rest AES-256-GCM encryption is intact. The real network-reachable exposures are: unauthenticated config tampering (create/modify/delete monitored services), redacted topology disclosure via `GET /config/services`, an SSRF primitive via `POST /setup/philips-bridge/pair`, and — most seriously — a route to the Pi command-injection finding below (unauthenticated RCE-on-relay). With the default `0.0.0.0` bind this is reachable by anyone on the LAN. Per ADR-017 the absence of auth is an intentional single-user/trusted-network decision; the actionable gaps are the `0.0.0.0` default and that `AGENTS.md` still advertises auth/CSRF/rate-limiting that do not exist.
**Fix:** Register an app-level `preHandler` that verifies a signed token/session for every route except health and the setup-status probe, failing closed (401). Prioritize `/config/export`, `/config/import`, and mutating routes. Share one verifier with the WS `AuthGate`.
Refs: `server.ts:27-71`, `routes/config.ts:43-124`, `routes/services.ts:38-49`, `ConfigStore.ts:454-472`, `index.ts:88-99`

### [high] WebSocket auth effectively disabled

`index.ts` registers `wsPlugin` with no `verifyToken`, so it falls back to `defaultVerifyToken()` returning `{ username: 'anonymous' }` and ignoring the token. `defaultExtractToken` only needs an `Authorization: Bearer <anything>` header. Any curl/wscat client on the network is "authenticated" and receives the full Broadcaster firehose — every service health/stats snapshot, leaking home-lab operational telemetry.
**Fix:** Wire a real `verifyToken` into the `wsPlugin` registration; make an unconfigured verifier a fatal startup error in production rather than silently authenticating as anonymous.
Refs: `index.ts:101-106`, `wsPlugin.ts:25-34,51`, `AuthGate.ts:37-46`

### [high] Command injection (RCE on relay) via config-controlled SSH command

`PiStatsCollector.fetchRpiInfo` builds `${c.nodePath} ${c.rpiCliPath} -H ${c.host}:${c.port} info` and runs it over SSH via `client.exec`, which passes the string through the remote login shell. `host`, `nodePath`, `rpiCliPath` are unconstrained strings writable through the open config API. A caller can set `host` to `x; rm -rf ~ #` and get arbitrary shell execution on the relay host on the next stats poll.
**Fix:** Validate host/port and paths at the schema level (strict regex, absolute-path allowlist), and pass argv as discrete tokens via a non-shell exec.
Refs: `PiStatsCollector.ts:226`, `config/services.ts:109-125`, `routes/config.ts:43-70`

### [high] SSH performs no host-key verification

Both `client.connect()` calls omit `hostVerifier`/`hostHash`, so ssh2 accepts ANY presented host key (no known_hosts/TOFU). A MITM on the path to a monitored host completes the handshake against the attacker's key, then the client sends authentication material (password/passphrase) and executes commands against the attacker.
**Fix:** Supply a `hostVerifier` in both files; persist the expected key TOFU as a per-instance config field (mirror the Hue `certHash` pattern); fail closed for password-auth hosts.
Refs: `sshExecutorImpl.ts:75-83`, `sshPool.ts:113-121`

### [high] TLS pinning is split-connection / TOCTOU

`createPinnedClient` calls `probeCertFingerprint(host,port)` which opens its OWN `tls.connect({ rejectUnauthorized:false })`, hashes that cert, compares to the pin, then calls `inner.send(req)` — the undici client, which opens a completely SEPARATE TLS connection with no cert options. The validated connection never carries the data, so a MITM can present the genuine cert to the probe and a different one to undici. The pin provides essentially no protection.
**Fix:** Pin on the connection that carries the request via a custom undici dispatcher/Agent with a `checkServerIdentity` SHA-256 check; remove the separate probe from the request path.
Refs: `pinnedClient.ts:17-19,54-64`, `client.ts:31-45`

### [high] Setup endpoints re-runnable, unauthenticated, an SSRF primitive

`GET /setup/status` (unauthenticated) leaks deployment state and `needsSetup` locks nothing, so setup/config writes are re-runnable anytime. `POST /setup/philips-bridge/pair` only checks `body.host` is non-empty, then passes it to `pairBridge` which builds `https://${host}/api` and probes with `rejectUnauthorized:false` — an unauthenticated SSRF primitive against any reachable `host:443` (cloud metadata, internal panels, LAN hosts).
**Fix:** Gate setup behind auth + a one-time bootstrap token invalidated after setup; restrict the pairing host to RFC1918/link-local, reject loopback/metadata, restrict to `https:443`.
Refs: `routes/setup.ts:15-62`, `huePairing.ts:24-49`, `pinnedClient.ts:19`, `client.ts:34-58`

### [high] Server binds `0.0.0.0` by default

`env.ts:6` defaults `BACKEND_V2_HOST` to `0.0.0.0`; `index.ts:118` listens on it. `trustProxy:true` implies an intended reverse proxy, but the default exposes the unauthenticated control plane to the whole LAN (and beyond if port-forwarded).
**Fix:** Default to `127.0.0.1`; require explicit opt-in for non-loopback, ideally only when auth is configured.
Refs: `env.ts:6`, `server.ts:31`, `index.ts:118`

### [high] Per-IP WS cap bypassable via spoofed `X-Forwarded-For`

`trustProxy:true` is set unconditionally, so Fastify computes `req.ip` from the client-supplied header. The WS cap keys on `req.ip`, so a direct client (the common self-hosted case) sends a unique XFF per connection to bypass the cap. With no global cap, this is a connection-exhaustion DoS.
**Fix:** Gate `trustProxy` on a trusted-proxy flag/CIDR; key the WS cap on `req.socket.remoteAddress`; add a global max-connections limit.
Refs: `server.ts:31`, `wsPlugin.ts:94,56`, `ConnectionManager.ts:19-26`

### [medium] Master key derived from arbitrary passphrase with unsalted single SHA-256

`deriveKey` falls through to `createHash('sha256').update(trimmed).digest()` if the key isn't 32-byte base64/hex; `env.ts` validates only `z.string().optional()` with no length/entropy requirement. `WATCHMAN_MASTER_KEY='hunter2'` yields key = SHA-256('hunter2'), so a stolen DuckDB file collapses to one SHA-256 guess per candidate — direct dictionary/rainbow attack.
**Fix:** Require a 32-byte key (remove the passphrase fallback), or run passphrases through scrypt/argon2 with a stored random salt; enforce minimum length in `env.ts`.
Refs: `encryption.ts:15-21,82`, `env.ts:9`

### [medium] No CSRF protection on any state-changing route

The CORS hook sets `Access-Control-Allow-Credentials:true` and advertises `X-CSRF-Token`, but no route reads or validates a CSRF token — there is no `@fastify/csrf-protection`. Currently partly inert (no cookies), but becomes live the moment cookie auth is added, at which point the broad localhost-credentialed CORS makes these endpoints trivially CSRF-able.
**Fix:** Implement the documented double-submit-cookie alongside the auth fix; reject mismatches with 403.
Refs: `server.ts:35-57`, `routes/config.ts:43-124`, `routes/services.ts:38-49`, `routes/setup.ts:26`

### [medium] No rate limiting on any HTTP route

No `@fastify/rate-limit` is installed or registered. `POST /services/:kind/control`, `/setup/philips-bridge/pair` (outbound work) and `/config/import` (DB writes) can be hammered freely — resource exhaustion, amplified outbound traffic, and (once auth exists) brute force. The 15s per-request timeout does not limit volume.
**Fix:** Register `@fastify/rate-limit` with global defaults and tighter per-category ceilings; key on a non-spoofable client IP (depends on the `trustProxy` fix).
Refs: `server.ts:59-68`, `package.json`

### [medium] No security headers; credentialed CORS reflects any localhost port

The CORS hook reflects any Origin starting with `watchman://`, `http://localhost:`, or `http://127.0.0.1:` and always pairs it with `Allow-Credentials:true`. No helmet/CSP/X-Frame-Options/X-Content-Type-Options. Exploitable once cookie auth is added.
**Fix:** Use `@fastify/cors` with an exact-origin allow-list; register `@fastify/helmet`.
Refs: `server.ts:35-57`

### [medium] Audit-log actor taken from an attacker-supplied `X-Actor` header

Every mutating handler derives `actor` from `req.headers['x-actor']` and persists it to the audit log. With no authenticated principal, the forensic record is fully spoofable and the free-form value is written unsanitized (log/record injection).
**Fix:** Derive actor from the verified principal once auth exists; until then, do not present it as trustworthy and escape before persisting.
Refs: `routes/config.ts:45-46,59,73,107,116`

### [medium] WS Origin validation disabled by default (no CSWSH protection)

`allowedOrigins` defaults to an empty Set; `enforceOrigin = size > 0`, so `isOriginAllowed` returns true for every Origin in production. No env feeds `FRONTEND_URL` into the WS plugin. Becomes a classic Cross-Site WebSocket Hijacking vector if cookie/JWT auth is added without origin enforcement.
**Fix:** Pass `allowedOrigins` from a `FRONTEND_URL`/`ALLOWED_ORIGINS` env var; default to enforcing in production.
Refs: `index.ts:101-106`, `wsPlugin.ts:48`, `AuthGate.ts:23-30`

### [medium] No inbound WS message handler or `maxPayload` limit

`@fastify/websocket` is registered with no options (default `maxPayload` 100 MiB), and the handler registers only `pong`/`close`/`error` — no `message` listener. Each connection can send 100 MiB frames the ws Receiver buffers with no consumer and no backpressure — memory-pressure DoS, amplified by the bypassable per-IP cap.
**Fix:** Set a small `maxPayload` (4–16 KiB) and attach a `ws.on('message')` that closes on any inbound frame.
Refs: `wsPlugin.ts:46,103-105`

### [medium] Service snapshots broadcast verbatim with no field allow-listing

`Broadcaster.broadcast` JSON-stringifies the whole poller snapshot to every client. `HealthSnapshot.details` and `StatsSnapshot.metrics` are open bags; whatever a collector places there (upstream error strings with URLs/tokens, internal IPs) is broadcast — to effectively any reachable host given the broken WS auth.
**Fix:** Apply an allow-list/redaction step before broadcast, mirroring the pino PII-redaction policy.
Refs: `Broadcaster.ts:22-27,53-67`, `poller.ts:82-103`, `BaseService.ts:26-43`

### [medium] Logger has no redaction despite documented PII redaction

`createLogger` builds pino with no `redact`, despite AGENTS.md stating "Structured JSON logging with PII redaction." Request logging is on; decrypted service configs flow through `ServiceLifecycle.createService`, and errors are logged as full objects. Any secret field incidentally logged is written in clear.
**Fix:** Add a pino `redact` config covering known secret field names and `req.headers.authorization`/`cookie`; strip query strings in `client.ts:55`; align AGENTS.md.
Refs: `logger.ts:9-25`, `server.ts:30`, `ServiceLifecycle.ts:60`, `client.ts:55`

### [low] GCM encryption uses no AAD — secret blobs are swappable

`encrypt`/`decrypt` never call `setAAD`; nothing ties ciphertext to its row/field. With DB write access, a blob can be copied onto another row and still decrypts under a different identity (secret relocation/confusion).
**Fix:** `setAAD` over `${id}|${kind}|${instanceId}` on both encrypt and decrypt.
Refs: `encryption.ts:49,72`, `ConfigStore.ts:280-282,168-171`

### [low] Master key stored in plaintext alongside the encrypted DB; chmod failures swallowed

`master.key` (mode 0o600) lives under the same `DATA_DIR` as the DuckDB ciphertext, so one backup/snapshot/dir-read compromises both halves. The `chmod` calls are wrapped in failure-swallowing try/catch.
**Fix:** Prefer supplying the key out-of-band; if a file is used, store it outside `DATA_DIR`; treat chmod failure as an error/warning.
Refs: `masterKey.ts:23,31-35`, `env.ts:8`

### [low] Usernames paired with stored passwords not redacted

`redactConfig` masks only the password/token side; `rpcUser`, `snmpUser`, `dsmAccount`, `sshUser`, etc. are returned in clear via `GET /config/services` and persisted in audit diffs — half of each credential pair disclosed to any caller.
**Fix:** Mask/partially-mask the account portion in API output, or document that usernames are intentionally cleartext; keep them out of long-lived audit diffs.
Refs: `ConfigStore.ts:115,367`, `fieldMetadata.ts:139,234,269`

### [low] WS authorization is binary — every user gets the full firehose

After `authenticate`, `Broadcaster.broadcast` sends every event to every open client regardless of stored user/meta; no per-service ACL or topic subscription. Limited impact today (one trust level) but unscoped if roles are ever added.
**Fix:** Introduce per-connection subscription topics + ACL check before send, or document that `/ws` is all-or-nothing.
Refs: `wsPlugin.ts:87-95`, `Broadcaster.ts:57`, `ConnectionManager.ts:25`

## Correctness

**Assessment:** No crashes-in-normal-use or data-loss bugs, but one user-visible high-severity defect (four service types never render) and a cluster of mediums that quietly break real-time updates and target the wrong service instance. Two through-lines: contract/namespace drift across the frontend boundary (camelCase vs lowercase kinds, `number` vs `string` timestamps, a WS payload the frontend never reads), and lifecycle/teardown gaps in the backend infra layer (pollers emit after teardown, timeouts and SSH channels leak, the DB "pool" grows unbounded, SSH reconnects forever). The recurring root cause is missing tests against real wire/key shapes — several bugs are masked by tests asserting fabricated payloads.

### [high] Renderer ServiceKind namespace diverges from backend kinds

The renderer layer keys on lowercase `philips`/`albyhub`/`macmini`/`raspi`, but backend canonical kinds are camelCase `philipsBridge`/`albyHub`/`macMini`/`raspberryPi`, returned un-normalized by `getInstances()`. `BentoDashboard` filters with `getRenderer(e.kind) && (configuredKinds[e.kind]?.count ?? 0) > 0` using the lowercase key, so `configuredKinds['macmini']` is undefined, count is 0, and the entry is dropped. These four service types never appear even when configured and online.
**Fix:** Unify on one namespace (rename renderer kinds + RENDERERS + ServiceKind + BENTO_LAYOUT to camelCase, or normalize at the API boundary); add a test asserting every renderer kind matches a backend kind.
Refs: `renderers/types.ts:5`, `renderers/index.ts:20`, `bentoLayout.ts:28`, `useServiceInstances.tsx:28`, `fieldMetadata.ts:104`

### [medium] WebSocket `service_update` invalidation is dead end-to-end

Two compounding contract bugs. (1) The frontend handler guards on `message.service` then calls `scheduleInvalidationForKey`, but the backend emits `{ scope, id, kind, instanceId, at, snapshot }` with NO `service` field — the guard is always false. (2) Even if fixed, the WS flush builds a 3-element query key while `useServiceStats` builds a 4-element key, so React Query prefix-matching can never match. The dashboard only refreshes via the 10s/30s polls; the entire debounce/batch invalidation machinery is unreachable. Tests pass because they fabricate `{ service: "adguard_main" }`, a shape that never occurs.
**Fix:** Derive the key from `message.kind`/`instanceId`; add scope/id/kind/instanceId to `WebSocketMessage`; share one query-key helper between hooks and the WS flush; test against the exact Broadcaster payload.
Refs: `useWebSocket.ts:194-198,116-117`, `Broadcaster.ts:22-27`, `useServiceHealth.ts:62-64`, `queryKeys.ts:11-12`

### [medium] Default instance routing is positional and shifts after any update/rename

`getByKind(kind)` with no instanceId returns `list[0]!`. `register()` appends; `applyUpdate` tears down then re-registers, re-appending at the END. So updating the index-0 instance moves it to the tail and `list[0]` resolves to a DIFFERENT instance. An instance-less `POST control {action:'restart'}` can silently hit an arbitrary instance.
**Fix:** Make the default deterministic (sort by instanceId, or store a stable default), or require instanceId when >1 instance exists and throw on ambiguity.
Refs: `ServiceRegistry.ts:24,13,39`, `ServiceLifecycle.ts:87`

### [medium] pinnedClient TOCTOU pin bypass

(Cross-listed with Security.) `send()` probes the cert on a separate `tls.connect` socket, then sends the real request over a different undici connection that is never pin-validated; also doubles TLS handshakes per request.
**Fix:** Validate the peer cert SHA-256 on the connection that carries the request; remove the separate probe round-trip.
Refs: `pinnedClient.ts:54-64,17-43`

### [medium] Detail sheet ignores `source:"health"` metrics → always "—"

`ServiceDetailSheet` renders both the header primary value and detail-group metrics via `format(dotGet(statsMetrics, key))`, never consulting `metric.source`, while `ServiceTile` correctly uses `pickSource()`. Health-sourced metrics (synology host/latency, roon `reachable`, etc.) live in `HealthSnapshot`, not metrics, so they render "—". Roon's primary summary metric is `reachable source:'health'`, so the detail header big number is permanently blank.
**Fix:** Export `pickSource()` to a shared module and use it in `ServiceDetailSheet` for both the header and detail metrics, passing `healthRaw`.
Refs: `ServiceDetailSheet.tsx:316,160`, `synology.ts:86`, `roon.ts:17`

### [medium] SSH exec timeout abandons the channel and leaks the abort listener

In `execOnReady` the timeout handler rejects but never removes the abort listener and never closes/destroys the exec stream; the channel keeps running on the shared persistent Client. Pi/Mac collectors run many execs, so each timed-out exec leaks a channel against ssh2's per-connection cap, eventually exhausting the connection.
**Fix:** Close/destroy the stream in both timeout and abort handlers; always remove the abort listener in `finish()`.
Refs: `sshPool.ts:52-54,43-82`

### [medium] SSH pool retries forever (fixed 2s, no backoff, no cap)

`RECONNECT_DELAY_MS` is a fixed 2s; both `error` and `close` schedule a reconnect. Only an unreadable key file stops retries — a refused/offline host reconnects indefinitely for the process lifetime. Contrast `wsClient.ts:85-95`, which does exponential backoff.
**Fix:** Add exponential backoff with a cap, reset on `ready`, consider lazy reconnect when no requests are pending.
Refs: `sshPool.ts:87-94,164-179,37`

### [medium] Poller emits stale events after teardown

`Task.cancel()` sets `cancelled` and clears the timer but does NOT abort an in-flight runner. When `teardown()` unregisters a service mid-tick, the in-flight check resolves and still emits `service.health.updated`/`stats.updated`/`error` for a service that no longer exists (ghost status broadcast to WS/caches). `poller.stop()` has the same gap and returns `Promise<void>` implying quiescence while late checks can still emit.
**Fix:** Per-task AbortController threaded into checkHealth/getStats and aborted in cancel()/stop(); guard every emit behind a `tasks.has(svc.id)`/`!cancelled` check after await; have stop() await in-flight runners with a bounded grace.
Refs: `poller.ts:67,78-107,129-133`, `ServiceLifecycle.ts:46`

### [low] `at` typed as string but OpenAPI contract is number

`openapi.yaml` (source of truth) declares `at: number` (ms) for both snapshots, but hand-written frontend types declare `at: string`, forcing defensive coercion and `useAggregatedHealth.ts:72` fabricating `at: String(Date.now())`. A non-numeric `at` breaks the `existing.lastT === snapshotAt` dedup in `metricHistory`.
**Fix:** Change types to `at: number`; fix `useAggregatedHealth.ts:72` to `Date.now()`; simplify the coercion.
Refs: `apiClient/types.ts:20,29`, `openapi.yaml:520,550-552`

### [low] `withTimeout()` leaks an uncleared, non-unref'd timer per request/tick

The timer is cleared only if the parent aborts first, never on normal completion, and isn't `.unref()`'d. Every HTTP call and poll tick leaves a pending timer holding a closure alive; because they aren't unref'd they keep the event loop alive, blocking prompt exit.
**Fix:** Return a disposable or accept an `onSettle` hook to `clearTimeout` on settle; at minimum `.unref()`; dispose in a `finally`.
Refs: `abort.ts:16-35`, `client.ts:36`, `poller.ts:79,94`

### [low] DuckDbPool.connect() pushes into an array never pruned

`connections.push(conn)` with no release API; `ConfigStore.withConn` closes connections itself, so closed references accumulate for the process lifetime — a steady JS memory leak proportional to total DB ops.
**Fix:** A real acquire/release pool, a self-removing wrapper close(), or stop tracking caller-managed connections.
Refs: `DuckDbPool.ts:21-26`, `ConfigStore.ts:149-160`

### [low] Frontend reconnect scheduled twice (onerror + onclose)

Both events fire on a failed connection; each increments `reconnectAttempts` and calls `scheduleReconnect` without clearing the prior timer, so one failure can double-count attempts and arm two timers. The test only fires `onclose`, so this path is untested.
**Fix:** Clear `reconnectTimeoutRef` at the top of `scheduleReconnect`; schedule only in `onclose`; add a test firing both events.
Refs: `useWebSocket.ts:313-345,264-268`

### [low] usePingServiceCard passes instanceId as the kind path param

`getServiceHealth(kind, instance?)` is called with a single arg, so `instanceId` is passed positionally as `kind` and the `?instance=` query is dropped — wrong URL for any multi-instance service. Harmless only because the hook is currently dead code.
**Fix:** Call with `(serviceKey, instanceId)`, or remove the hook if unused.
Refs: `usePingServiceCard.ts:34,42`, `endpoints.ts:39-53`

### [low] qBittorrent rows use `Math.random()` as React key

`key={t.hash ?? t.name ?? Math.random().toString(36)}` generates a fresh key each render when both are missing, unmounting/remounting rows on every stats poll/WS tick.
**Fix:** Use a stable fallback like `idx-${i}`.
Refs: `qbittorrent.tsx:82`

### [low] ReviewStep shows a check icon for disabled services

The status chip renders `<Check/>` then `{svc.enabled ? 'Enabled' : 'Disabled'}` unconditionally, so a disabled service shows a green checkmark next to "Disabled."
**Fix:** Conditionally render the icon (neutral/minus when disabled).
Refs: `ReviewStep.tsx:42`

## Performance

**Assessment:** Mixed, dominated by a gap between documented architecture and wired reality: the SWR cache, circuit breaker, and keep-alive HTTP agent pool are all built and exported but never instantiated, so every poll and HTTP read hits live downstream services with no de-duplication, no backoff, no tuned connection reuse. This compounds with a redundant read path (`GET /services` re-runs a full fleet-wide fan-out per request, per tab) and per-call session/connection churn. The frontend has a parallel pattern (global refetch-on-focus fanning into N requests; unstable object identities defeating memoization). Most issues are medium/low at home-lab scale, but two packaging issues stand out: the `geist` font misclassification breaks `--omit=dev`, and React Query Devtools ships in the prod build.

### [medium] geist font in devDependencies breaks `--omit=dev` build

`package.json` declares `geist` under devDependencies, but `fonts.css` references its woff2 files by hard-coded relative paths into `node_modules` and those fonts are part of the shipped UI. A standard `npm ci --omit=dev` (normal in CI/Docker prod) won't install geist, so Vite can't resolve the font URLs — build break or broken webfonts.
**Fix:** Move `geist` to dependencies; replace the `../../../../node_modules/...` URLs with a resolvable import.
Refs: `package.json:44`, `fonts.css:11,19`

### [medium] SWR cache is dead code

`createSwrCache` has zero non-test callers; `GetServiceStatus` calls services directly and `index.ts` wires the registry with no cache. Every HTTP request and poll tick hits the real downstream service with no fresh/stale reuse and no single-flight de-duplication — concurrent callers each issue independent live requests.
**Fix:** Resolve `GetServiceStatus`/`GetAggregatedHealth` through a per-(service,scope) SwrCache keyed by service id, using the stored `cacheTtlMs`.
Refs: `swr.ts:27`, `GetServiceStatus.ts:11,16`, `index.ts:88`

### [medium] `GET /services` fans out live health checks per request, per tab

The handler runs `aggregated.run`, which does a live `checkHealth` against EVERY registered service. `useAggregatedHealth` defaults to a 10s `refetchInterval`, while the poller already polls the same checkHealth on `healthMs` and broadcasts over WS. With N services and T tabs that is N×(1+T) live checks per ~10s window.
**Fix:** Serve `GET /services` from the last poller snapshot rather than re-running checkHealth per request.
Refs: `routes/services.ts:15`, `GetAggregatedHealth.ts:14`, `useAggregatedHealth.ts:25,41`

### [medium] Circuit breaker never wired

`createBreaker` has zero non-test callers; the poller calls checkHealth/getStats directly. When a service is down, every health (~10s) and stats (~30s) tick keeps issuing full-timeout requests against the dead endpoint indefinitely, burning a full timeout window per tick.
**Fix:** Wrap per-service checkHealth/getStats in the poller (and on-demand path) in a per-service `Breaker.exec`.
Refs: `breaker.ts:27`, `index.ts:45`, `poller.ts:78`

### [medium] HTTP keep-alive agent pool never injected

`createAgentPool` (undici Agent with connection/keep-alive tuning) has no callers; `createHttpClient()` is built with no dispatcher, so all service polling falls back to undici's global default — no per-origin cap or keep-alive, risking connection churn and TLS re-handshakes per poll.
**Fix:** Instantiate `createAgentPool()` once and pass it as the dispatcher to `createHttpClient({ dispatcher })`.
Refs: `agentPool.ts:10`, `client.ts:31`, `index.ts:47`

### [medium] On-demand status/control routes create AbortSignals with no timeout

`const newSignal = () => new AbortController().signal;` — never aborted, no timeout — is passed into all four handlers. Contrast the poller's `withTimeout`. A stalled downstream ties up a request with no upper bound; `GET /services`' fan-out has no aggregate deadline.
**Fix:** Build the signal via `withTimeout` linked to the request lifecycle; add an overall deadline to `GetAggregatedHealth.run`.
Refs: `routes/services.ts:13,16,23,32`

### [low] Global `refetchOnWindowFocus:true` fans into N per-tile requests

`App.tsx` sets it globally; each `ServiceTile` mounts its own `useServiceStats`. On every focus, React Query refetches every tile's stats query simultaneously — a synchronized burst hammering per-service pollers/breakers.
**Fix:** Disable focus refetch in `useServiceStats` (keep the 30s interval), or aggregate stats like health.
Refs: `App.tsx:39`, `useServiceHealth.ts:55,74`, `ServiceTile.tsx:129`

### [low] Aggregated-health refetch re-renders every tile every 10s; offline tiles defeat memoization

`useAggregatedHealth` refetches every 10s and its queryFn always returns a fresh object, so every tile re-renders (and `ServiceTile` isn't `React.memo`'d). For offline services, `resultToSnapshot` returns a new literal with non-deterministic `at: String(Date.now())` each call, so downstream `useMemo`s recompute every render.
**Fix:** Build the offline snapshot once per entry, drop the non-deterministic `at`, memoize `pickHealth` per kind/instance, wrap `ServiceTile` in `React.memo`.
Refs: `useAggregatedHealth.ts:25,39,65`, `useServiceHealth.ts:43`, `ServiceTile.tsx:124,136,156,390`

### [low] React Query Devtools (224 KB) is a prod dependency and ships as a chunk

`@tanstack/react-query-devtools` is under dependencies, statically imported at module top, rendered behind a DEV gate. The committed prod build emits a 224 KB chunk; relying on Vite DCE of the gate is fragile.
**Fix:** Move to devDependencies and convert to a DEV-gated lazy/dynamic import.
Refs: `package.json:31`, `App.tsx:3,103`, `dist/assets/B5PP2USH.CZRijM_s.js`

### [low] useWebSocketEvent resubscribes on handler identity change

The JSDoc claims a ref-stable contract, but the effect depends on `[type, handler]` with no ref — any inline handler resubscribes every render. The sole current consumer is memoized, so impact is nil today but the contract is false.
**Fix:** Implement the documented ref pattern (handler in a ref, depend only on `[type]`).
Refs: `useWebSocketEvent.ts:16,21`

### [low] DuckDbPool is not a pool — every connect() leaks a reference

(Same root cause as the Correctness DuckDbPool finding.) New connection per call appended to an array only cleared in `close()`; no reuse, unbounded growth of closed handles.
**Fix:** A real fixed-size pool, or splice each connection out on caller close.
Refs: `DuckDbPool.ts:21,24`, `ConfigStore.ts:149`

### [low] Bitcoin checkHealth/getStats duplicate RPCs on independent intervals

`checkHealth` issues getblockchaininfo + getnetworkinfo; `getStats` re-fetches the same two plus more. The poller schedules health (~10s) and stats (~30s) as independent timers with no shared result, so both RPCs are fetched twice. The pattern repeats across services with no cache.
**Fix:** Share a short-TTL cached result (the SWR single-flight covers this once wired), or derive health from the stats fetch when intervals align.
Refs: `BitcoinService.ts:151,172`, `poller.ts:78,93`

### [low] SNMP getter opens/tears down a fresh v3 session per get/walk

`get()`/`walk()` create and close a session per call, re-deriving v3 auth/priv key localization every tick for Synology/Router.
**Fix:** Cache/reuse a v3 session per (host, credentials) for the service lifetime; close on stop.
Refs: `snmpGetterImpl.ts:52,76`, `SynologyService.ts:100,138`

### [low] manualChunks omits several shipped UI deps

`vite.config.ts` chunks only react/router/three Radix packages/react-query, but several deps (popover, scroll-area, toggle, sonner, lucide, tailwind-merge, cva) land in the entry chunk, so any app change busts that vendor cache.
**Fix:** Add the remaining vendor packages to manual chunks, or use a function routing `node_modules` into per-package vendor chunks.
Refs: `vite.config.ts:99`, `package.json:24`

### [low] Tailwind content globs point at non-existent dirs

`content` lists `./pages`, `./components`, `./app` that don't exist at the top level; only `./src/**` matches. Cosmetic confusion; purge works.
**Fix:** Remove the dead globs, keep `./src/**/*.{ts,tsx}`.
Refs: `tailwind.config.ts:7`

### [info] Redundant double console/debugger stripping

Both terser `drop_console`/`drop_debugger` and `esbuild.drop` are configured for prod — dropped twice, slower build, ambiguous intended minifier.
**Fix:** Pick one path.
Refs: `vite.config.ts:89,138`

### [info] Backend emits source maps unconditionally (92 .map files)

`sourceMap:true` with no prod override; harmless server-side but extra artifacts and a minor disclosure risk if `dist/` were ever served.
**Fix:** Disable for release builds, or accept for server stack traces and never serve `dist/*.map`.
Refs: `tsconfig.json:23`, `dist/index.js.map`

## Architecture

**Assessment:** Functional but suffering pervasive intent/reality drift. The dominant through-line is "documented but never wired" — the circuit breaker, SWR cache, OpenAPI type-generation pipeline, and core/container DI interface are all advertised (ADR-013, AGENTS.md, ADR-004) but absent from the actual composition root, while the declared "dependencies flow downward only" layering is violated by upward and bidirectional imports. A second is split-brain vocabularies on the frontend: two service-kind casings (hiding 4 of 13 services), two parallel health shapes bridged by ad-hoc adapters, two dead legacy stat models, and phantom service kinds with no backend.

### [high] Renderer/kind casing split-brain hides 4 of 13 services

(Same defect as the Correctness high finding, viewed architecturally: no normalization layer exists between the backend's camelCase canonical kinds and the frontend's lowercase renderer/layout keys.)
**Fix:** Establish one canonical kind vocabulary; add a regression test asserting every backend kind has a renderer + bento entry.
Refs: `renderers/index.ts`, `renderers/types.ts`, `bentoLayout.ts`, `BentoDashboard.tsx`, `useServiceInstances.tsx`, `kindCategories.ts`, `registerServices.ts`

### [medium] Circuit breaker is dead code — contradicts accepted ADR-013

`createBreaker()`/`metrics.registerBreaker()` have no production call sites; the poller calls services directly. ADR-013 (accepted) states the poller "Integrates with circuit breaker (skip poll if circuit open)." The documented reliability guarantee does not exist.
**Fix:** Wire `createBreaker` per service into `poller.track()` and `registerBreaker`, or delete `infra/circuitBreaker`, remove breakers from `MetricsSnapshot`, and write a superseding ADR.
Refs: `breaker.ts`, `poller.ts`, `metrics.ts`, `docs/adr/013-backend-rewrite-typescript-fastify.md`

### [medium] SWR cache has zero production consumers; HTTP live-probes every service per request

A repo-wide grep finds no consumers. The poller's results are never stored or read by the HTTP layer. ADR-013 promises "in-process LRU caching with SWR pattern." Push (poller→bus→WS) and pull (HTTP) paths duplicate all work; `/services` is as slow as the slowest probe (bounded only by the 15s request timeout).
**Fix:** Introduce a last-snapshot store populated by poller bus events; read cached snapshots in `GetServiceStatus`/`GetAggregatedHealth`; register via `metrics.registerCache`.
Refs: `swr.ts`, `GetAggregatedHealth.ts`, `GetServiceStatus.ts`, `routes/services.ts`, ADR-013

### [medium] "Dependencies flow downward only" layering is violated

`application/ServiceLifecycle.ts` imports `createService` from `bootstrap/registerServices.ts` (upward; bootstrap isn't even in the layer list). `infra/scheduler/poller.ts` imports `domain/BaseService` while domain services value-import infra (`PhilipsBridgeService`→`createPinnedClient`, `homebridgeClient`→`createJwtClient`), making domain↔infra a runtime cycle. The clean-architecture claim in the source-of-truth ADR is neither enforced nor true.
**Fix:** Move `createService` into application/a factory module; have domain services depend on infra interfaces (type-only) with concrete factories injected; update ADR-013 to match or document exceptions.
Refs: `ServiceLifecycle.ts`, `registerServices.ts`, `poller.ts`, `PhilipsBridgeService.ts`, `homebridgeClient.ts`, ADR-013

### [medium] OpenAPI-first contract is fiction — generated.ts never generated

`generate:types` is defined and AGENTS.md says `openapi.yaml` is the source of truth, but `generated.ts` does not exist in the tree and no frontend file imports OpenAPI-derived types. The real contract is hand-maintained in `apiClient/types.ts`. The documented compile-time bridge does not operate; types can silently drift.
**Fix:** Either wire `generate:types` into CI/prebuild and migrate to importing from `generated.ts`, or drop the script + AGENTS.md claim and declare `apiClient/types.ts` the hand-maintained source.
Refs: `package.json`, `apiClient/types.ts`, `types/api.ts`, `types/server.ts`

### [medium] Renderer health contract lies about its shape

`RendererContext.health` is typed as `{status}` ServiceHealth from `@/types/api`, but the real API `HealthSnapshot` is `{reachable, latencyMs, host,...}`. `ServiceTile` bridges with a throwaway `healthShape` for tone/subtitle while passing raw `HealthSnapshot` to `pickSource` — two shapes through one contract, reconciled by `as` casts. A renderer author writing `health.status` for a health-sourced key gets undefined.
**Fix:** Type `RendererContext.health` as the real `HealthSnapshot`; derive offline/warn from `reachable`/`message`; remove the per-consumer adapter.
Refs: `renderers/types.ts`, `ServiceTile.tsx`, `apiClient/types.ts`, `bitcoin.ts`

### [medium] AGENTS.md/ADR-004 overstate the security stack

`server.ts` registers no JWT/cookie/CSRF/rate-limit/helmet; `package.json` has none of those deps. The removal is intentional and documented in ADR-017 (single-user, trusted-network), so this is not an auth regression — but AGENTS.md still asserts the controls exist, ADR-004's superseded banner still lists `@fastify/helmet`, and the CORS hook advertises a dangling `X-CSRF-Token` nothing consumes.
**Fix:** Reconcile AGENTS.md with ADR-017; fix ADR-004's note; remove `X-CSRF-Token` from CORS allow-headers; add at least a shared-secret/rate-limit gate on config-mutation routes if any non-trusted-LAN deployment is intended.
Refs: `server.ts`, `package.json`, ADR-004, ADR-017

### [low] Two dead legacy data models coexist with the live renderer model

`dashboardData.ts`, `dashboardStatus.ts`, `types/server.ts`, and per-service interfaces in `types/api.ts` are imported only by their own tests; the live dashboard uses the flat renderer model. Dead weight kept "covered" only by tests, misleading readers and inviting reuse of the wrong model.
**Fix:** Delete them (and their tests), or move behind a clearly-marked WIP path with an ADR note. Keep one stats model.
Refs: `types/server.ts`, `types/api.ts`, `dashboardData.ts`, `dashboardStatus.ts`

### [low] `/metrics` advertises breaker/cache subsystems that are never registered

`snapshot()` returns `{ breakers, poller, cache, process }`, but `index.ts` only calls `setPollerStats`. `/metrics` always reports `breakers:{}` and `cache:{}`, implying running-but-empty subsystems that aren't wired.
**Fix:** Register them once wired, or remove the fields so `/metrics` reflects only what runs.
Refs: `metrics.ts`, `index.ts`, `routes/metrics.ts`

### [low] Route-level AbortSignal is decorative

(Same root as the Performance no-timeout finding, viewed architecturally.) The never-aborted signal is threaded into every service call on the HTTP path, so the AbortSignal abstraction every service implements is a no-op there.
**Fix:** Thread a real bounded signal derived from the request lifecycle with an explicit timeout.
Refs: `routes/services.ts`, `routes/config.ts`, `plugins/requestTimeout.ts`

### [low] Phantom service kinds (beryl, telenet, nostrcheck) wired across the frontend

`ServiceKind` includes three kinds with no renderer and no backend service. `BENTO_LAYOUT` adds a permanently-dead `nostrcheck` tile; `useWebSocket` special-cases beryl/telenet; `dashboardStatus` branches on all three.
**Fix:** Remove them from `ServiceKind`/`BENTO_LAYOUT`/invalidation logic until a backend ships, or gate behind a TODO/ADR.
Refs: `renderers/types.ts`, `bentoLayout.ts`, `useWebSocket.ts`, `dashboardStatus.ts`

### [low] core/container.ts DI interface is dead code

`interface Container` has no importers; `index.ts` hand-rolls composition and the interface omits things actually wired (metrics, store, lifecycle). New contributors may try to extend it with no effect.
**Fix:** Delete it, or make `index.ts` build and consume a `Container` as the single composition contract.
Refs: `core/container.ts`, `index.ts`

### [low] Real-time state split across three uncoordinated stores

react-query (server state), module-singleton WS globals with a hand-rolled subscriber Set, and the in-memory `metricHistory` ring buffer coexist, glued by `key.split('_')` string parsing that must stay manually aligned with `queryKeys`. metricHistory only updates on refetch, so WS metric events don't directly feed sparklines.
**Fix:** Document the intended boundary in an ADR; replace the `key.split('_')` heuristic with an explicit `{kind,instanceId}` message contract; consider feeding WS metric payloads into metricHistory directly.
Refs: `useWebSocket.ts`, `metricHistory.ts`, `useServiceHealth.ts`, `WebSocketProvider.tsx`

## Code Design

**Assessment:** Sound at the macro level, but design discipline frays at the edges. Two through-lines: value-resolution drift in the frontend (two same-named `ServiceHealth` types and two divergent metric-value paths producing real blank/`[object Object]` defects that `strict:false` hides), and pervasive DRY erosion (per-service HTTP/error helpers, the health-tone preamble, tone/status/duration formatters, numeric coercers each copied across 3–13 sites). Plus two stated-convention violations (systemic `null` usage; stateless single-method application classes) and ~400 lines of dead pre-renderer code.

### [medium] Two conflicting ServiceHealth types and two value-resolution paths

Two unrelated interfaces both named `ServiceHealth` coexist (`{status}` in `api.ts` vs `{reachable,...}` HealthSnapshot in `apiClient/types.ts`). `pickSource` resolves `source:'health'` keys against the HealthSnapshot, but `ServiceDetailSheet` resolves every detail metric with bare `dotGet(statsMetrics, key)`, ignoring `metric.source` — so health-sourced detail metrics are permanently blank, and where honored, a key like synology `{key:'host', source:'health'}` yields `[object Object]`. `strict:false` hides the mismatch.
**Fix:** Rename one interface; extract `pickSource` into a shared resolver used by both tile and sheet; make the contract explicit about which health object `source:'health'` keys read from.
Refs: `types/api.ts:2`, `apiClient/types.ts:8`, `renderers/types.ts:55`, `ServiceTile.tsx:90,95`, `ServiceDetailSheet.tsx:316`, `synology.ts:86`, `roon.ts:26`

### [medium] ~400 lines of dead pre-renderer-architecture code

`dashboardData.ts` (167 lines), `dashboardStatus.ts` (155 lines), `types/server.ts`, and most of `lib/utils.ts` formatters have no non-test consumers; the live `BentoDashboard` uses none of it. `dashboardStatus.ts` hardcodes beryl/telenet/nostrcheck branches contradicting the data-driven design; the utils formatters duplicate `renderers/formatters.ts` with divergent conventions. Violates "code = truth."
**Fix:** Delete the dead modules and their tests (keep `cn`); document any intentionally-retained module.
Refs: `dashboardData.ts:40`, `dashboardStatus.ts:64`, `types/server.ts:1`, `lib/utils.ts:11`

### [medium] Systemic `null` violates the explicit "never use null" convention

AGENTS.md: "Backend (TS): NEVER use null — use undefined." The shared metric type bakes it in (`StatsMetricValue = ... | null`), and services emit `?? null` en masse (~63 occurrences) plus 30+ `= null` initializers across infra. Mixing null/undefined forces consumers to check both and serializes null into the public stats envelope.
**Fix:** Remove `null` from `StatsMetricValue`; switch to `undefined` (omit or `| undefined`); use undefined for internal state. Document any deliberate exception in AGENTS.md.
Refs: `BaseService.ts:32`, `AdGuardService.ts:167`, `IpfsService.ts:103`, `MacMiniService.ts:103`, `PiStatsCollector.ts:8`

### [low] tone() health-status preamble duplicated across all 13 renderers

All 13 open `tone()` with the identical two-line offline/warning preamble; several are only that preamble plus `return 'ok'`. A change to the health-to-tone mapping requires editing 13 files.
**Fix:** Add a shared `healthTone(health)` helper; let renderers do `return healthTone(health) ?? <specific logic>`.
Refs: `bitcoin.ts:86`, `synology.ts:119`, `qbittorrent.tsx:225`, `ipfs.ts:66`, `homebridge.ts:47`, `philipsBridge.ts:43`

### [low] Duplicated per-service HTTP parse/assert-ok/error-envelope logic

Each HTTP service reimplements near-identical `parse<T>`/status-error prologue/JSON-or-text fallback; the catch envelope recurs at 14 sites across 10 files. Divergence has already crept in (IPFS falls back to raw text, AdGuard doesn't).
**Fix:** Extract `assertOk(res, ctx)`, `parseJsonOrText<T>(res)`, and a `toUnavailable(e, ctx)` wrapper into `infra/http`/`core`.
Refs: `AdGuardService.ts:203`, `QBittorrentService.ts:270`, `IpfsService.ts:196`, `BitcoinService.ts:247`, `TorService.ts:379`

### [low] Per-component duplication of TONE_TO_STATUS, fmtMs, Badge ternary, duration formatting

`TONE_TO_STATUS`, `fmtMs`, the tone→Badge ternary, and the spark-tone map are each defined identically in 2+ components; day/hour/min duration formatting is reimplemented in 3 places.
**Fix:** Move shared maps/helpers into a `tonePresentation.ts` module; consolidate duration formatting.
Refs: `ServiceTile.tsx:26,312`, `ServiceDetailSheet.tsx:40`, `ChartsPanel.tsx:5`

### [low] Application-layer "classes" are stateless single-method wrappers

AGENTS.md says prefer functions; these four are not BaseService subclasses and hold only an injected registry with thin methods — the exact anti-pattern the convention calls out.
**Fix:** Convert to plain functions, or document why the exception extends beyond service classes.
Refs: `GetServiceStatus.ts:8`, `GetAggregatedHealth.ts:11`, `ListInstances.ts:9`, `ControlService.ts:7`

### [low] Inconsistent DI shape and inline Result construction in the application layer

## Testing

**Assessment:** Moderately unhealthy. The suite has reasonable breadth but its coverage is structurally misleading and does not protect the highest-risk paths. Three through-lines: (1) coverage theater — tests assert the current insecure/unimplemented behavior as correct, one frontend test no-ops React's `useEffect`, and many Settings/setup specs only check that a component renders over a fully-mocked data layer; (2) security- and recovery-critical leaf modules are untested where it matters most (config export/import round-trip, master-key lifecycle, breaker half-open concurrency, central HTTP client); (3) end-to-end protection is effectively absent (one trivial smoke spec, not wired into CI).

### [high] Route tests bless an unauthenticated, actor-forgeable API

`buildServer()` registers no auth/CSRF/rate-limit and `package.json` has none of those deps, yet every state-changing route test injects unauthenticated requests and asserts 201/200/204, and a test asserts the `x-actor` header is trusted verbatim. The documented security model is unimplemented AND the tests pin the insecure behavior as correct — CI would have to be rewritten to add auth.
**Fix:** If auth/CSRF/rate-limit are required (per AGENTS.md), add the middleware and tests asserting 401 on missing JWT, 403 on missing CSRF, and actor from the authenticated principal. If intentionally dropped (ADR-017), correct AGENTS.md and pin the documented access model so drift can't recur silently.
Refs: `server.ts`, `routes/config.ts`, `routes/config.test.ts`, `package.json`

### [medium] ConfigStore export/import round-trip has no real-store test

`exportAll()`/`importBundle()` (the backup/restore path) are never called in the real-DuckDB store test; the route test stubs the store entirely, so the encrypt→base64→decrypt→merge logic never executes. A bug in encoding, decryption, or update-vs-create merge would silently corrupt or drop configs (incl. secrets) on restore.
**Fix:** Add ConfigStore tests against in-memory DuckDB + real encryptor: round-trip incl. secrets, import-over-existing counts, malformed entries to skipped/errors, wrong-key/tampered bundle throws.
Refs: `ConfigStore.ts`, `ConfigStore.test.ts`, `routes/config.test.ts`

### [medium] E2E suite is one trivial smoke spec, not run in CI

The entire e2e directory is one spec asserting `#root` is attached and the title matches `/watchman/i`; `ci.yml` runs only vitest with no Playwright step. None of the defining journeys (login, setup wizard, add/edit/delete service, dashboard tiles, WS updates) are guarded.
**Fix:** Add Playwright specs for the highest-value journeys and a `test-e2e` CI job so e2e actually gates merges.
Refs: `tests/e2e/smoke.spec.ts`, `playwright.config.ts`, `package.json`, `.github/workflows/ci.yml`

### [medium] Central frontend HTTP client has no unit tests

`core.ts` (retry/backoff, in-flight dedup, timeout/abort composition, envelope parsing) has no test; `configApi.test.ts` mocks `request` entirely. A regression could silently retry non-idempotent POSTs, collide/leak the dedup map, or mis-classify timeout/non-JSON failures.
**Fix:** Add `core.test.ts` with stubbed fetch + fake timers: GET retries on 503 but POST doesn't; concurrent identical GETs share one fetch and the key clears; timeout yields AbortError; non-JSON 200 and 204 handled; `!ok` surfaces `extractApiError`.
Refs: `apiClient/core.ts`, `configApi.test.ts`

### [medium] masterKey.ts is completely untested

`loadOrCreateMasterKey()` (the root of the encryption scheme) has no test. Regressions are silent and security-relevant: loose key permissions, regenerating a new key (making all configs undecryptable), or mishandling empty-file/override cases.
**Fix:** Test (using `fs.mkdtemp`): env override short-circuits; first call generates a 32-byte key with mode 0o600; second call returns the same key; empty file throws. Skip the mode assertion on non-POSIX platforms.
Refs: `masterKey.ts`

### [medium] Circuit-breaker half-open concurrency gating is untested

`breaker.test.ts` only exercises single-call half-open transitions with the default `halfOpenMaxCalls=1`, so the `tryAcquire` gate and `halfOpenInFlight` decrement never run. The concurrency limit is the entire point of half-open.
**Fix:** Add tests with `halfOpenMaxCalls=2`: 3 concurrent execs admit exactly 2 and reject the 3rd; an admitted half-open failure correctly admits/rejects the next call.
Refs: `breaker.ts`, `breaker.test.ts`

### [medium] useServiceHealth test mocks React useEffect to a no-op

`vi.mock('react', ... useEffect: vi.fn())` means the effect calling `recordStats` (the metric-history path feeding sparklines) never runs, and the `at`-coercion branch has no coverage — yet the v8 gate counts these lines as exercised by import.
**Fix:** Render the hook in jsdom (don't mock useEffect), or extract the recording logic into a pure helper and test it directly across numeric/string-numeric/missing `at`.
Refs: `useServiceHealth.test.ts`, `useServiceHealth.ts`

### [medium] ServiceEditor tests cover only the instance-id rename path

All six cases touch only the Instance ID input; there is no test for required-field validation, url/number coercion, secret-field handling, or the test-connection flow — the most user-facing Settings logic.
**Fix:** Add tests: submit blocked on empty required url; number fields coerce; Test-connection calls `mutateAsync` and renders success/error; secrets handled (not echoed) on edit.
Refs: `ServiceEditor.test.tsx`, `ServiceEditor.tsx`

### [low] BackupRestore import has only a render smoke test

`handleImport` parse/error/result branches (malformed JSON → error, success counts, per-entry errors, file-input reset) are unexercised, despite import overwriting real configs.
**Fix:** Mount with `useImportConfig` mocked; feed a valid bundle and assert counts/error list; feed malformed JSON and assert the error; assert the file input clears.
Refs: `BackupRestore.tsx`, `settings.smoke.test.tsx`

### [low] BackgroundPoller pause/resume and untrack paths are untested

Tests cover only track/emit/stop/duplicate; nothing advances the clock while paused, asserts resume restarts emission, or verifies untrack stops one service while others tick.
**Fix:** Using the FakeClock harness: pause → advance → assert no emit; resume → advance → assert emit. Track two, untrack one, assert only the other emits.
Refs: `poller.ts`, `poller.test.ts`

### [low] Settings/setup tests are mostly shallow render checks over mocked data

Audit/BackupRestore/Services and ReviewStep/ConfigureStep specs assert only a `<main>`/static labels with react-query/configApi fully stubbed — guarding only against import/render crashes.
**Fix:** Promote the highest-value smoke tests to behavior tests (ReviewStep with non-empty addedIds; ConfigureStep through un-stubbed ServiceEditor onSubmit; Services page rows + delete mutation).
Refs: `settings.smoke.test.tsx`, `steps.smoke.test.tsx`

### [low] createSshExecutor is untested; sshPool tests cover a different implementation

`createSshExecutor` (own connect/exec/timeout/abort/auth-classification + key-file read) is never imported outside its own file; the thorough SSH tests exercise `createSshPool`, a separate implementation. Either dead code masquerading as covered, or a live untested security-adjacent path.
**Fix:** Confirm usage. If dead, remove it. If used, test it mirroring `sshPool.test.ts` (success, exec/connect error → Unavailable, auth → Unauthorized, timeout, abort, unreadable key → Unauthorized).
Refs: `sshExecutorImpl.ts`, `sshPool.test.ts`

### [low] Several tests use real wall-clock sleeps and single-flush microtask waits

`abort.test.ts`/`clock.test.ts`/`eventSubscription.test.ts` sleep real ms with margin assertions; the poller relies on a single `setImmediate` flush that races if the tick chain gains an await — classic CI flakiness despite an injectable FakeClock.
**Fix:** Drive time with FakeClock + an explicit microtask-drain helper where injectable; widen margins or use fake timers for unavoidable real-timer cases.
Refs: `abort.test.ts`, `clock.test.ts`, `eventSubscription.test.ts`, `poller.test.ts`

## UX

**Assessment:** Middling. Two recurring through-lines hurt real users. First, destructive and state-changing actions in Settings are inconsistently guarded — delete uses a ConfirmDialog while restore (the most destructive) fires immediately on file selection, and several mutations silently swallow errors. Second, accessibility and redundant-encoding are partial — status dots, sparklines, connection state, and test/error results convey meaning by color or hover-only tooltips with no live regions, so a service going offline is not announced to screen-reader or color-blind users. The single most impactful structural gap is the complete absence of a responsive layout.

### [medium] Restore (import) overwrites configs immediately on file select

`handleImport` parses the file and immediately calls `importMut.mutateAsync(bundle)` with no confirmation or preview — the most destructive action in Settings, yet the least guarded (delete requires a ConfirmDialog).
**Fix:** Stage the parsed bundle, show a ConfirmDialog summarizing updates vs creates, mutate only on explicit confirm.
Refs: `BackupRestore.tsx:29-44,89-96`

### [medium] Dashboard has no responsive layout

`DashboardGrid` uses a fixed `grid-cols-12` with no breakpoints; tile column spans are unconditional. On a ~375px phone tiles become unreadable and sparklines clip. The repo ships an unused `use-mobile` hook.
**Fix:** Make the grid responsive (`grid-cols-1 sm:grid-cols-6 xl:grid-cols-12`), add breakpoint-scoped col-span variants, reduce small-screen padding, consider `useIsMobile` to stack.
Refs: `DashboardGrid.tsx:14-21`, `tileVariants.ts:15-20`, `BentoDashboard.tsx:62`

### [medium] Delete failure leaves the confirm dialog stuck open with no error

On a rejected `mutateAsync`, the throw propagates and `setPendingDelete(null)` never runs, so the dialog stays open; nothing renders `deleteMut.error`. The user gets zero feedback.
**Fix:** try/catch the delete, surface `deleteMut.error` in the dialog, close only on success. Apply the same pattern to create/update.
Refs: `Services.tsx:137-150`, `ConfirmDialog.tsx:36-44`

### [medium] Enable/Disable toggle is fire-and-forget with no error feedback

Non-async `updateMut.mutate(...)` with no `onError`, no per-row pending state, and no error rendering. On a failed request the toggle silently appears to do nothing, leading to double-clicks.
**Fix:** Track per-row pending and surface `updateMut.error`; consider an optimistic update with rollback.
Refs: `Services.tsx:76-87`, `useConfigQueries.ts:81-98`

### [medium] Real-time status/connection changes not announced to screen readers

`StatusDot` has `role="status"` but no `aria-live` and an empty body — only its `aria-label`/`data-state` changes, which AT does not re-announce. The TopNav connection dot conveys state only via color + a silently-flipping title. The core real-time event (a service going offline) is announced to nobody.
**Fix:** Add a visually-hidden `aria-live` region emitting a sentence on status transitions; mirror WS connection state into a live region/toast.
Refs: `StatusDot.tsx:41-49`, `ServiceTile.tsx:246-265`, `TopNav.tsx:164-173`

### [low] ErrorBoundary dumps a raw stack trace (expanded) in production

The fallback always renders `<details open>` with `error.stack` + `componentStack`, no `import.meta.env.DEV` guard — intimidating, unactionable, and leaks internal structure, violating the production-safe-stack-trace guidance honored on the backend.
**Fix:** Gate the stack `<details>` behind `import.meta.env.DEV`; in prod show only the message + Try Again.
Refs: `ErrorBoundary.tsx:57-70`

### [low] "WebSocket connected" success toast fires on every reconnect

The backend sends `connection` on every open and the client unconditionally `toast.success`es it; the reconnect machinery re-fires it on each drop. On a flaky network the user gets a stream of green toasts while the useful signal (the drop) gets none.
**Fix:** Suppress the toast on initial/expected connect; toast only on recovery after a prior disconnect; add a "Reconnecting…" indicator; dedupe via a stable toast id.

### [low] StatusDot "online" pulse renders in the wrong color

The dot sets only background per tone and never `color`, but the pulse ring uses `after:bg-current` — so the healthy pulse inherits the surrounding text color (grey/white) instead of `--ok`, looking like a rendering bug.

`handleSubmit` validates only `selectedKind`/`instanceId`; `FieldInput` shows `*` but never sets `required` and has no per-field error. A user can submit an empty required `apiUrl`, with feedback only as one generic server-round-trip message — extra friction during onboarding.

## Themes

Cross-cutting patterns that recur across dimensions and point at root causes rather than isolated bugs:

- **Doc/code drift on load-bearing claims.** AGENTS.md and ADRs advertise mechanisms that don't exist in code: auth/CSRF/rate-limit/helmet (Security, Architecture, Testing), PII redaction (Security), the OpenAPI-first type pipeline (Architecture), "dependencies flow downward only" (Architecture), and the Express-vs-Fastify stack note. The docs are the stated source of truth, so this actively misleads contributors and operators. ADR-017 documents the auth removal intentionally — but nobody reconciled the rest of the docs with it. **Reconciling AGENTS.md/ADRs with reality is a high-leverage, low-cost fix.**

- **"Built but never wired" infrastructure.** The circuit breaker, SWR cache, keep-alive agent pool, `core/container` DI interface, and `createSshExecutor` are all implemented and exported but have no production call sites. They show up across Performance, Architecture, and Testing. `/metrics` even reports empty breaker/cache subsystems as if they run. This is the most concentrated cluster: each is either a quick wire-up or a delete-plus-ADR.

- **Fail-open / fail-silent defaults.** WS auth accepts anything; origin enforcement is off when unconfigured; the server binds all interfaces; on-demand AbortSignals never fire; chmod failures are swallowed; mutation errors (delete, toggle) are silently dropped in the UI. The system defaults to permissive/quiet rather than safe/loud.

- **Frontend namespace/shape split-brain.** Two service-kind casings (hiding 4 services), two `ServiceHealth` types, two metric-value resolution paths, two dead legacy stat models, phantom service kinds, and a WS payload the frontend never reads. `strict:false` lets these mismatches compile. The recurring fix is a single canonical vocabulary + a regression test.

- **Tests pin the wrong shape / the wrong behavior.** Route tests bless the unauthenticated API; the WS test fabricates a `{service}` payload that never occurs; a hook test no-ops `useEffect`; Settings/setup specs render over fully-mocked data. Several real bugs (dead WS push path, blank detail metrics) survive precisely because tests assert fabricated shapes. Coverage numbers overstate real protection.

- **Untested security/recovery leaf modules.** The master-key lifecycle, config export/import round-trip, breaker half-open gate, and the central HTTP client — the modules where a silent regression is most damaging — have no real tests.

## Coverage & gaps

This review was a static, read-only pass over `apps/backend` and `apps/frontend` source plus committed `dist/` artifacts. Honest boundaries and where to go deeper:

**Under-covered within scope:**

- **Security depth.** This was a code-reading pass, not a pen-test. No dynamic exploitation, fuzzing, or full SSRF/redirect-chain tracing was performed. Input validation was spot-checked (notably the Pi command-injection path), not exhaustively traced across all 14+ service config schemas. Given the unauthenticated control plane plus the RCE/SSRF primitives, **Security warrants a dedicated deeper pass** — particularly a full audit of every Zod schema field that reaches a shell, URL, or SNMP/SSH parameter, and a decision-record cleanup against ADR-017.
- **Concurrency/race conditions.** Beyond the identified teardown-emit and double-reconnect races, the poller/scheduler/eventBus/Broadcaster interaction under churn (rapid add/update/delete during active polling) was reasoned about but not stress-tested.
- **DuckDB persistence semantics.** Migration/schema-versioning, concurrent-write behavior, and the import-merge transactionality were reviewed at the code level but not exercised against the real engine.
- **The standardized response envelope and OpenAPI spec** were treated as the contract but not validated end-to-end (no request/response conformance testing against `openapi.yaml`).

**NOT examined at all (explicit out-of-scope):**

- **`apps/desktop` (Electron).** The desktop main/preload process, IPC surface, `nodeIntegration`/`contextIsolation` settings, and auto-update were not reviewed. Electron commonly carries its own significant security surface (remote content, IPC, fuses) — this is a notable blind spot worth its own review.
- **`packages/*` shared workspaces.** Not inspected; findings focused on backend/frontend apps.
- **Devcontainer / Dockerfile / launcher scripts.** The git status shows active work on `.devcontainer/Dockerfile` and recent commits on egress firewall, binary pinning, and a host memory live-share. None of this was reviewed despite being security-relevant (the firewall hardening and "live-share project memory with the host" especially). **The devcontainer/supply-chain hardening deserves its own pass.**
- **`install.sh` / deployment / CI pipeline internals.** `.github/workflows/ci.yml` was referenced only via the Testing findings (no e2e job); the broader pipeline, release packaging, and any install scripts were not audited.
- **Dependency CVEs / supply chain.** No `npm audit`, lockfile, or transitive-dependency CVE analysis was run. AGENTS.md's "Audit new dependencies" guidance was not verified. The recent `neoip`-override-for-`ip` commit suggests dependency risk is already on the radar — a dedicated `npm audit` + lockfile review is recommended.
- **Runtime/observability in production.** Log volume/retention, the actual deployment topology (is there really a reverse proxy in front?), and TLS termination were inferred from `trustProxy:true`, not confirmed.

**Confidence note:** Findings tagged in the source summaries as "verifier confidence medium" (notably the on-demand-timeout latent-hang, the 10s re-render cost, the SNMP/Bitcoin session-churn items) are real mechanisms but their production impact depends on runtime conditions not measured here. The critical/high security findings, the four-services-never-render bug, and the dead-WS-push-path bug are high-confidence and directly evidenced.
