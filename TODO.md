## Correctness / bugs

- [x] 🔺 **C1 — WebSocket `service_update` never invalidates query caches (real-time updates silently broken).** `apps/backend/src/transport/ws/Broadcaster.ts:22-27` emits `{ type:'service_update', scope, id, kind, instanceId, at, snapshot }` with **no `service` field**. The frontend `apps/frontend/src/hooks/useWebSocket.ts:194-199` only acts on a `service_update` when `message.service` is truthy (`if (message.service) scheduleInvalidationForKey(message.service)`). Since `service` is always `undefined`, **no invalidation ever fires from health/stats updates** — the dashboard updates only via React Query `refetchInterval` (10s health / 30s stats), not the WebSocket. The whole real-time pipeline is effectively dead for service updates. Fix: align the contract — either emit `service`/a canonical key from the broadcaster, or have the client invalidate from `kind`+`instanceId` (and the aggregated-health query) on every `service_update`.
- [x] ⏫ **C2 — Philips Hue certificate pinning is broken end-to-end (and TOCTOU).** `apps/backend/src/infra/http/pinnedClient.ts:51-66` probes the TLS cert on one connection (`tls.connect({ rejectUnauthorized:false })`), compares the SHA-256, then issues the **actual** request through the unmodified undici client (`inner.send`), which performs **default TLS verification**. A Hue bridge presents a self-signed / hostname-mismatched cert, so `inner.send` rejects it and every pinned request fails (`probeApi`/`fetchLightMetrics` swallow it → light stats silently empty whenever `certHash` is set). Separately, check-cert-then-send over two independent sockets is a time-of-check/time-of-use gap — the pin is never enforced on the connection that carries data. Fix: pin on the real request path (custom undici `connect`/checkServerIdentity or a pinned dispatcher), not a throwaway probe socket.
- [x] ⏫ **C3 — No authentication / CSRF / rate-limiting on the v2 backend, contradicting CLAUDE.md.** The only Fastify plugins are `@fastify/compress` and `@fastify/websocket` (`apps/backend/package.json`); there is no JWT, cookie, CSRF, or rate-limit code anywhere in `apps/backend/src` (grep confirms). CLAUDE.md's Security section claims the project "Maintain[s] JWT auth, CSRF double-submit, and tiered rate limiting," and CORS even advertises an `X-CSRF-Token` header (`server.ts:47`) that nothing validates. Meanwhile `BACKEND_V2_HOST` defaults to `0.0.0.0` (`config/env.ts:6`) and the `/config/*` routes create/update/delete services and export config. Anyone who can reach the port can reconfigure the box. Either this is "trusted-network single-user by design" (as `openapi.yaml` info says) — in which case CLAUDE.md is wrong and should be corrected — or auth needs to exist. Pick one and make docs+code agree.
- [x] 🔼 **C4 — `zmqConnect` is never wired, so Bitcoin ZMQ real-time block streaming is dead code.** `BitcoinService` accepts an optional `zmqConnect` dep and an `onStart` that subscribes to `hashblock` (`domain/services/bitcoin/BitcoinService.ts:117-137`), but `bootstrap/registerServices.ts:71-72` constructs it as `new BitcoinService({ http, ping, config, now })` — no `zmqConnect`. So `onStart` always early-returns, the `zmq*` config fields (`zmqHashblockEndpoint`/`zmqRawtxEndpoint`) do nothing, and the entire `infra/zmq/*` module (with tests) is unreachable in production. Also `onStart:120-124` has a dead `if` block whose body is only a comment. Fix: wire a real `ZmqConnectFn` into `infra` and pass it through `buildService`, or remove the feature + fields + infra if abandoned.
- [x] 🔼 **C5 — Per-request `AbortSignal`s are inert; HTTP request timeout doesn't cancel service work.** Every HTTP route builds `newSignal = () => new AbortController().signal` (`routes/services.ts:13`, `routes/config.ts:15`) — a signal with no controller reference, so it can never be aborted. The `requestTimeout` plugin (`plugins/requestTimeout.ts`) replies 504 but does not abort the in-flight health/stats work, which keeps running (and on `/services` runs `checkHealth` for _every_ service). Service-level `timeoutMs` is the only real bound. Fix: thread a real, request-scoped `AbortController` (abort on `reply.raw` close/timeout) into the application services.
- [x] 🔼 **C6 — Multi-instance id parsing splits on `_` but ids can't contain `_`.** Instance ids are validated against `^[a-z0-9][a-z0-9-]*$` (`config/store/ConfigStore.ts:17`) — hyphens allowed, underscores forbidden. Yet `dashboardData.getInstanceNumber` does `instanceId.split("_")[1]` (`components/dashboard/dashboardData.ts:124-132`) and `useWebSocket` derives `baseServiceKey = key.split("_")[0]` (`hooks/useWebSocket.ts:113-114`). Both assume `kind_N` underscore ids. With hyphenated ids the instance number is never parsed and the WS key-family routing (when it eventually receives a key) is wrong. Fix: settle on one id convention and parse consistently.

## Performance

- [x] 🔼 **P1 — `DuckDbPool` leaks connection references unboundedly and never actually pools.** `infra/db/DuckDbPool.ts:21-26`: every `connect()` pushes the new connection into a `connections[]` array that is only drained on `close()`. `ConfigStore.withConn` opens a fresh connection per call and `closeSync()`s it in `finally`, but the pool keeps the (now-closed) reference forever. Each config read/write/audit/`loadAll` grows the array by one for the process lifetime → steady memory growth on a long-running daemon. It's also not a pool (no reuse, no cap). Fix: either remove closed connections from the array, or implement a real bounded pool with reuse.
- [x] 🔼 **P2 — `/services` aggregated health hits every service synchronously on each HTTP read, bypassing the poller's cached state.** `application/GetAggregatedHealth.ts:14-26` calls `s.checkHealth(signal)` live for all services on every `GET /services`. With the dashboard's `useAggregatedHealth` polling every 10s plus `refetchOnWindowFocus`, each poll fans out N live network probes (ping + HTTP per service) even though the background poller already computed fresh health and published it on the bus. The openapi description claims "HTTP reads serve cached/poller-published state," but they don't — there's no read-through cache of the latest snapshot. Fix: maintain a latest-snapshot map updated from `service.health.updated` events and serve that from `/services`.
- [x] 🔽 **P3 — qBittorrent `/torrents/info` fetches the full torrent list every stats cycle.** `domain/services/qbittorrent/QBittorrentService.ts:123` pulls all torrents each poll only to sort and slice the top 20 by speed (`:177-180`), in addition to the incremental `maindata`. For large seedboxes this is a lot of repeated payload every 30s. Consider `?filter=active&sort=...&limit=` or deriving the active set from the already-synced `maindata`.

## Batch 2 — frontend↔backend contract & functionality

- [x] 🔺 **C7 — Frontend/backend service-kind vocabularies disagree; 4 of 13 service types are completely non-functional in the UI.** The backend kinds (`config/schemas/fieldMetadata.ts:19-32`) are camelCase: `albyHub`, `macMini`, `philipsBridge`, `raspberryPi`. The frontend's `ServiceKind` union, `BENTO_LAYOUT`, and `RENDERERS` map use different strings: `albyhub`, `macmini`, `philips`, `raspi` (`renderers/types.ts:5-21`, `config/bentoLayout.ts:19-34`, `renderers/index.ts:20-34`; renderer `kind` fields confirmed e.g. `macMini.ts:20 kind:"macmini"`). The dashboard keys configured services by the **backend** kind returned from `/instances` (no normalization layer — `ListInstances.all()` returns `s.kind` verbatim, `useServiceInstances.groupByKind` buckets by it), then filters `BENTO_LAYOUT` with `getRenderer(e.kind) && configuredKinds[e.kind]?.count > 0` (`BentoDashboard.tsx:34-36`). For the 4 camelCase kinds `configuredKinds["macmini"]` is `undefined` → count 0 → **tile never renders**; and even if it did, `useServiceStats("macmini")` calls `GET /services/macmini/stats` → `registry.getByKind("macmini")` → `NotFoundError`. So AlbyHub, Mac Mini, Philips Hue, and Raspberry Pi can be configured but never appear/work on the dashboard. The other 9 kinds coincidentally match and work. **Root cause pinned:** the inconsistency is internal to the frontend — the setup flow's `kindCategories.ts` uses the _correct_ backend kinds (`albyHub`, `macMini`, `philipsBridge`, `raspberryPi`), so setup happily creates these services; only the dashboard renderer layer (`renderers/*`, `bentoLayout`, the `ServiceKind` union) invented the lowercase variants. So the canonical strings are the backend camelCase ones — fix the renderer layer to match (not the other way). Also remove dead frontend kinds `beryl`/`telenet`/`nostrcheck` that have no backend equivalent (and `nostrcheck` in BENTO_LAYOUT has no renderer at all).
- [x] ⏫ **C8 — Service errors never reach the client; the "Events" tab and error toasts are dead.** The poller emits `service.error` on the bus (`infra/scheduler/poller.ts:90,105`), but `Broadcaster.start()` only subscribes to `service.health.updated`, `service.stats.updated`, and the three `config:*` events (`transport/ws/Broadcaster.ts:21-37`) — **never `service.error`**. `Broadcaster.alert()` exists but has no caller anywhere in the backend (grep confirms). The detail sheet's Events tab only listens for `alert` WS messages (`ServiceDetailSheet.tsx:138-156`), and `useWebSocket` only toasts on `alert`. Net: no service failure is ever surfaced in real time; the Events tab is permanently empty. Fix: subscribe the broadcaster to `service.error` and emit an `alert` (or a dedicated error frame), and/or have `service_update` carry the error.
- [x] 🔽 **C9 — Synology DSM password is sent in the URL query string.** `infra/synology/dsmClient.ts:52-60,99` puts `passwd=` and `_sid=` in the request URL. Even over HTTPS, URLs are the most likely thing to end up in proxy logs, error messages, or APM traces. The thrown errors here don't include the URL today, but it's fragile. Prefer POST form body for login where DSM supports it, and ensure no logger ever records outgoing request URLs.
- [x] 🔽 **C10 — `pickHealth` fabricates a `HealthSnapshot` with `at` as a string, diverging from the real shape.** `hooks/useAggregatedHealth.ts:65-74` returns `{ reachable:false, message, at: String(Date.now()) } as unknown as HealthSnapshot` on error, while the real snapshot uses `at:number`. The `as unknown as` cast hides the type hole; any consumer doing numeric math on `at` (e.g. staleness checks) breaks for errored entries. Use a consistent numeric `at`.

With reconnect-on-drop this becomes noisy (a toast every time the socket flaps). Demote to a debug log or only toast on transition from a previously-failed state.
- [x] 🔽 **UX2 — Setup gate can be bypassed and is racy with dismissal.** `App.tsx:50-56` `SetupGate` redirects to `/setup` only for `/`; the `/settings/*` routes are not gated, and `useSetupDismissal` lets a user dismiss setup permanently client-side. Low impact for a single-user tool, but worth confirming it's intended that an unconfigured instance can navigate straight to settings.

## Batch 3 — unwired infrastructure (dead resiliency/caching layers)

- [x] ⏫ **A3 — Circuit breaker infrastructure is fully built + tested but never wired into any service.** `infra/circuitBreaker/breaker.ts` (`createBreaker`) is imported by nobody; `MetricsRegistry.registerBreaker` is never called (grep: zero call sites outside the registry definition). No service wraps its outbound calls in a breaker, so the "Circuit Breaker (prevents hammering failing services)" that CLAUDE.md lists as a core domain concept **does not exist at runtime** — a hard-down service is re-probed at full rate every poll forever. `GET /metrics` always returns `breakers: {}`, and the TopNav breaker warning badge (`TopNav.tsx:155-162`, `useBackendMetrics`) is dead code that can never light up. Fix: wrap each service's network calls in a per-instance breaker and `registerBreaker` it, or delete the module + metrics field + UI badge and correct the docs.
- [x] ⏫ **A4 — SWR cache is built + tested but never wired, and `cacheTtlMs` is a no-op setting.** `infra/cache/swr.ts` (`createSwrCache`) has no call sites; `MetricsRegistry.registerCache` is never called → `GET /metrics` always returns `cache: {}`. Critically, the per-service `cacheTtlMs` field — defined in every schema (`config/services.ts:13`), stored in its own DB column (`migrations.ts:11`), and surfaced in the ServiceEditor "Advanced" panel (`ServiceEditor.tsx:276-287`) — is **read by nothing**. Users can set it but it does nothing. This is also the missing piece behind P2: a read-through SWR cache keyed per service is exactly what would let `GET /services` serve poller-published state instead of re-probing live. Fix: wire SWR (or remove the field + UI + infra). Cross-ref P2.
- [x] 🔼 **C11 — Updating a service via the editor/API silently resets `pollPolicy` to defaults.** `ConfigStore.update` calls `mergeSecretsWithExisting` (`ConfigStore.ts:533-551`), which re-injects only secret fields and `kind` from the existing record — **not** `pollPolicy`. `ServiceEditor` never renders or submits `pollPolicy` (it's not in `kind.fields`; only `instanceId/enabled/cacheTtlMs/timeoutMs` are common — `ServiceEditor.tsx:24-30`). So any update of a service that had a non-default `pollPolicy` (e.g. set via env-migration or import) falls through to `ServiceInstanceSchema`'s defaults (`healthMs:10000, statsMs:30000`). Custom poll cadence is lost on the next save. Fix: preserve existing `pollPolicy` (and confirm `cacheTtlMs`/`timeoutMs`) on partial update, or round-trip them through the editor.

## Batch 3 — security / observability

- [x] 🔼 **SEC1 — Logger configures no PII/secret redaction, but request logging is on.** `core/logger.ts` builds pino with no `redact` option, while the server sets `disableRequestLogging: false` (`server.ts:30`) so every non-sampled request is logged with method/url. URLs can carry secrets — notably the Synology DSM `passwd`/`_sid` query params (C9) and any `Authorization` header pino's serializers include. CLAUDE.md explicitly promises "Structured JSON logging with PII redaction" and "never log tokens/PII," so this is doc/impl drift with a real leak path into logs. Fix: add `redact: { paths: [...], censor: '[redacted]' }` for auth headers, cookies, and known secret query keys.
- [x] 🔽 **OBS1 — `service.error` poller failures are logged but otherwise invisible.** Combined with C8, a failing service surfaces only as a swallowed bus event; there's no error counter in `/metrics`, no breaker trip (since A3 breakers don't exist), and no client alert. Operators have no aggregate signal that a service is flapping. Consider an error/health counter in the metrics snapshot.

## Batch 3 — dead code / metric accuracy

- [x] 🔽 **D3 — Several fully-built, tested infra modules are never imported in the runtime.** Beyond A3/A4/C4: `infra/ws/wsClient.ts` (backend WS client) has no importers (grep). The pattern — breaker, SWR cache, ZMQ subscriber, backend wsClient, and `GpioController` (D2) all carry tests but no wiring — suggests either an unfinished integration or abandoned features. Each adds maintenance/coverage cost and misleads readers (and CLAUDE.md/architecture docs) about what the system actually does. Decide per module: wire it or delete it.

## Batch 4 — WebSocket transport & probe efficiency

- [x] 🔺 **C12 — The WebSocket can never connect from a browser/Electron client; the entire real-time layer is dead in the shipped app.** `wsPlugin` is registered in `index.ts:101-106` with no `extractToken`/`verifyToken`/`allowedOrigins`, so it uses `defaultExtractToken` (`transport/ws/wsPlugin.ts:25-30`), which requires an `Authorization: Bearer …` header. The frontend connects with `new WebSocket(url)` (`hooks/useWebSocket.ts:301`) and the browser WebSocket API **cannot set request headers** on the handshake — no `Authorization` is ever sent. So `gate.authenticate` returns `{ok:false}` and the server immediately `socket.close(1008, 'No authentication token provided')` (`wsPlugin.ts:87-91`). The client sees a non-1000 close, retries 5× (`MAX_RECONNECT_ATTEMPTS`), then toasts "WebSocket connection failed after multiple attempts" — and the TopNav status dot is permanently red. This makes C1 moot (no socket to deliver `service_update` over) and means **all** live behavior (health/stats push, config-change push, alerts) is non-functional; the UI is polling-only. Secondary issues with the same gate: `defaultVerifyToken` returns `{username:'anonymous'}` for _any_ token (no real verification), and `allowedOrigins` defaults to empty → origin checks disabled — so the intended auth is also theater. Fix: extract the token from a cookie or `?token=`/`Sec-WebSocket-Protocol` (things a browser can actually send), or drop the token requirement for the trusted-network model and gate on origin instead. Cross-ref C1, C3.
- [x] 🔼 **P6 — AlbyHub legacy probe mode (the default) path-scans the host on every poll.** `legacyProbe` defaults to `true` (`config/services.ts:72`). In that mode each stats cycle runs `resolveInfo` — up to 11 sequential `GET`s over `INFO_PATHS` (`AlbyHubService.ts:18-30,217-232`) — and may then call `probe` (up to 7 more over `PROBE_PATHS`), while each health cycle runs `probe` (up to 7). So a single instance can fire ~7 (health/10s) + ~18 (stats/30s) sequential requests per cycle, re-scanning the same candidate paths forever, with `resolveInfo` and `probe` overlapping. Fix: cache the first successfully-resolved endpoint and reuse it; consider defaulting to the deterministic NWC mode (2 requests).
- [x] 🔽 **C13 — `service_update` carries `id = "{kind}:{instanceId}"` but the client's key handling assumes a flat service key.** Even after C12/C1 are fixed, the broadcaster's `id` is colon-joined (`BaseService.id`), while `useWebSocket.scheduleInvalidationForKey` treats the key as `kind` or `kind_N` and splits on `_` (`useWebSocket.ts:113-130`, see C6). Any reconnect fix must also define which field the client keys off (`kind`+`instanceId` vs `id`) and parse it consistently, or invalidations will target the wrong query families. Cross-ref C1, C6.

## Batch 5 — reconnect logic, enum drift, legacy frontend

- [x] 🔼 **C14 — WebSocket reconnect attempts are double-counted and a timer is leaked on failed connects.** In `useWebSocket`, both `onerror` (`:334-345`) and `onclose` (`:313-332`) increment `reconnectAttempts` and call `scheduleReconnect()`. A failed connection fires `onerror` _then_ `onclose`, so each failure counts as two attempts and schedules two reconnects; the second `scheduleReconnect` overwrites `reconnectTimeoutRef.current`, leaking the first timer (which still fires `connect()` later). Net effect: `MAX_RECONNECT_ATTEMPTS` (5) is exhausted after ~2–3 real attempts, and connect can be invoked twice per cycle (mostly absorbed by the 5s throttle). With C12 keeping every connect doomed, this makes the client give up almost immediately. Fix: guard so a single failure advances the counter once (e.g. only handle reconnect in `onclose`, and clear any pending timer before scheduling).
- [x] 🔽 **C15 — Breaker `state` enum mismatch between backend and frontend.** Backend `BreakerState` is `'half-open'` (hyphen, `infra/circuitBreaker/breaker.ts:4`); the frontend `BreakerMetrics.state` type and `summarizeBreakers` compare against `'half_open'` (underscore, `hooks/useBackendMetrics.ts:6,52`). Half-open breakers would be counted as closed. Latent today because breakers are never emitted (A3), but it will silently undercount the moment A3 is fixed. The frontend type also drops `openedAt`. Align the enum.
- [x] 🔽 **D4 — Dead/legacy frontend hooks with wrong API usage.** `hooks/usePingServiceCard.ts` has no callers (grep) and is broken: it calls `apiClient.getServiceHealth(instanceId)` / `getServiceStats(instanceId)` passing the **instanceId into the `kind` parameter** (`endpoints.ts:39-53` — first arg is `kind`), and it parses a legacy v1 envelope (`{ status:"online", data:{ host, ping, ports } }`) the v2 API never returns. Its dependency `useEnabledServices.isServiceEnabled` also lowercases names before matching `/kinds` output, which is camelCase (`macMini` etc.) — so it returns false for those kinds (same root cause as C7). Remove these legacy hooks or rewrite against the v2 contract.
- [x] 🔽 **ACC1 addendum — Synology RX/TX use 32-bit single-interface counters too.** `SynologyService` reads `networkRx`/`networkTx` from `1.3.6.1.2.1.2.2.1.10.1` / `…16.1` (`SynologyService.ts:32-33`) — hard-coded `ifIndex=1`, 32-bit, same wrap/rate caveat as ACC1. Reports raw cumulative values. Same fix (64-bit HC counters + rate).

## Batch 6 — startup robustness, docs drift, CORS

- [x] 🔼 **A5 — `lifecycle.start()` runs service `onStart` hooks sequentially with no timeout, and the HTTP server won't listen until they all finish.** `main()` awaits `lifecycle.start()` (`index.ts:84`) before `buildServer`/`app.listen` (`:88,118`). `start()` → `reloadAll()` → `for (const s of all) await bringUp(s)` (`ServiceLifecycle.ts:120-134`), and `bringUp` `await`s each `svc.onStart()` (`:58-72`) inside the serialized chain with the poller paused. `onStart` does real network I/O — Roon connects to the core and may wait on extension pairing (`RoonService.onStart:50-58`), Tor connects to ControlPort + `setevents` (`TorService.onStart`), Bitcoin would connect ZMQ. There's a try/catch but **no timeout**: a single slow/hanging `onStart` delays every later service's bring-up and prevents `app.listen` from ever running, so the whole API (and health probe) is unreachable until it resolves. Fix: bound each `onStart` with a timeout, bring services up concurrently, and/or start listening before/independently of service bring-up.
- [x] 🔼 **DOC1 — CLAUDE.md's "Required backend" env vars don't exist in the codebase.** CLAUDE.md (Environment) states "Required backend: `AUTH_USERNAME`, `AUTH_PASSWORD_HASH` (bcrypt), `JWT_SECRET` (≥32 chars), `FRONTEND_URL`." None of these are referenced anywhere in `apps/backend/src` (grep returns nothing). The real schema (`config/env.ts`) only knows `NODE_ENV`, `BACKEND_V2_PORT`, `BACKEND_V2_HOST`, `LOG_LEVEL`, `DATA_DIR`, `WATCHMAN_MASTER_KEY` — and `.env.example` matches _that_, not CLAUDE.md.
